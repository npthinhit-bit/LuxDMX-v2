# M0.4.4.4 — Web/static asset generator decision record

**Dự án:** LuxDMX-v2  
**Milestone:** M0.4.4  
**Work package:** M0.4.4.4 — Web/static asset generator nếu đủ evidence  
**Ngày:** 22-08-2026  
**Baseline:** `9928301 build: add deterministic template generator`  
**Trạng thái:** **Blocked / documented-only**

## 1. Quyết định

M0.4.4.4 **chưa đủ evidence để triển khai web/static asset generator**. Thư mục `webui/` và nội dung web được firmware phục vụ hiện tại không phải cùng một source-of-truth đã được chứng minh. Chúng khác nhau về cấu trúc trang, route/API contract, asset URL, nội dung và byte-level hash; một số `webui` files không có runtime route tương ứng.

Do đó, work package này không tạo generated header, không gzip/encode `webui/`, không thêm PlatformIO/CMake hook và không thay đổi inline runtime assets. Việc generator hóa lúc này có thể thay thế nhầm dashboard/setup behavior hoặc tạo output mà firmware không consume.

> **Kết luận:** `webui/` hiện được phân loại là **tracked frontend source / candidate input**, không phải canonical firmware asset source. Cần một work package riêng để chọn source-of-truth và reconcile frontend/runtime contract trước khi viết generator asset.

The `webui/index.html` file identifies itself as a setup portal, loads `css/style.css`, `js/transport.js` and `js/app.js`, and initializes `LuxDMXApp`. This is structurally different from the firmware root page, which is a dashboard and references `/assets/style.css` and `/assets/app.js`.

### 2.2. Current firmware consumers

The firmware build registers `components/lux_web/src/web_frontend.c` and `components/lux_web/src/web_assets.c` directly in `components/lux_web/CMakeLists.txt`. The route layer calls `web_frontend_get_index()`, `web_frontend_get_config()`, `web_frontend_get_setup()`, `web_frontend_get_firmware()` and `web_assets_get(uri)` from compiled C strings [1] [2] [3]. No generated include directory or custom asset command is present in the current PlatformIO/CMake path [4] [5].

| Runtime route/resource | Current consumer | Current source | `webui/` mapping |
|---|---|---|---|
| `/` | `web_frontend_get_index()` | Inline `index_html` in `web_frontend.c` | No exact match; `webui/index.html` is a setup portal |
| `/config` | `web_frontend_get_config()` | Inline `config_html` in `web_frontend.c` | No `webui/config.html` |
| `/setup` | `web_frontend_get_setup()` | Inline `setup_html` in `web_frontend.c` | No separate `webui/setup.html`; behavior differs from tracked portal structure |
| `/firmware` | `web_frontend_get_firmware()` | Inline `firmware_html` in `web_frontend.c` | No `webui/firmware.html` |
| `/assets/style.css` | `web_assets_get()` | Inline CSS string in `web_assets.c` | Candidate `webui/css/style.css`, but not byte-identical |
| `/assets/app.js` | `web_assets_get()` | Inline JavaScript string in `web_assets.c` | Candidate `webui/js/app.js`, but not byte-identical and behavior differs |
| `/assets/transport.js` | No current route match found | None | Tracked file has no confirmed firmware consumer |

## 3. Byte/content comparison

A temporary C-string extraction check reconstructed the runtime strings and compared them with corresponding `webui` files. The check was performed at baseline commit `9928301`; it did not modify repository files.

| Pair | Runtime bytes | `webui` bytes | Exact match | Interpretation |
|---|---:|---:|---|---|
| Runtime root `index_html` vs `webui/index.html` | 4,827 | 3,232 | No | Different page role and DOM |
| Runtime `/assets/style.css` vs `webui/css/style.css` | 3,666 | 6,145 | No | Different CSS source/content |
| Runtime `/assets/app.js` vs `webui/js/app.js` | 1,641 | 7,928 | No | Dashboard polling versus setup provisioning behavior |
| Runtime `config_html` | 2,672 | No counterpart | N/A | Missing tracked source |
| Runtime `setup_html` | 3,439 | No counterpart | N/A | Missing exact tracked source |
| Runtime `firmware_html` | 5,512 | No counterpart | N/A | Missing tracked source |
| `webui/js/transport.js` | No runtime counterpart | 5,000 | N/A | Unconsumed candidate |

The differences are semantic, not only formatting. The tracked `webui/app.js` exposes a setup flow (`scan`, `selectNetwork`, `saveCredentials`) and depends on `createTransport()`/`MockTransport`; the runtime inline `app.js` periodically fetches `/info.json` and updates dashboard fields. Copying or embedding `webui/app.js` would therefore change the served firmware behavior.

## 4. Required evidence before unblocking

M0.4.4.4 can be reopened only after a source-of-truth decision is approved and recorded. At minimum, the next implementation package must provide:

1. A route-to-file mapping for every served HTML/CSS/JS resource, including `/`, `/config`, `/setup`, `/firmware`, `/assets/style.css`, `/assets/app.js` and any transport file.
2. A decision whether `webui/` replaces the current inline runtime pages, the inline C strings become canonical and `webui/` is removed/archived, or the two surfaces remain intentionally separate.
3. A byte/content migration test that proves every generated asset is the intended runtime asset, including HTML references, MIME type, URI prefix and API contract.
4. A consumer compile/runtime test proving generated outputs are actually served by `web_routes.c`; a manifest alone is not sufficient.
5. An explicit encoding/compression contract for text and binary assets. If gzip is chosen, metadata such as mtime and OS marker must be reproducible.
6. A bounded asset allowlist and maximum per-file/total size policy, using the existing generated manifest and hygiene conventions.

Until these conditions exist, no `webui` file should be copied into generated firmware output and no asset generator should be connected to the build.

## 5. Status and next boundary

M0.4.4.4 is **not implemented** because its precondition was intentionally not met. This is a controlled outcome, not a failed generator implementation. The evidence and blocking decision are complete; the next safe boundary is a separate frontend/runtime reconciliation package. M0.4.4.5 build-hook integration must not consume web assets until this record is resolved.

PCB, schematic, layout, BOM, Gerber, fabrication and electrical validation remain excluded.
